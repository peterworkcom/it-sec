# CSRF Basics

> CSRF -> Cross-site request forgery

The attacker causes the victim to carry out an action unintentionally. Like change the email address on their account, to change their password, or to make a funds transfer, can result to take full control.

## 3 key conditions for csrf

- `A relevant action`: An action within the application that can be exploited, such as changing the user's own password.

- `Cookie-based session handling`: The application relies solely on session cookies to identify the user who has made the requests.

- `No unpredictable request parameters`: The requests that perform the action do not contain any parameters whose values the attacker cannot determine or guess. For example, need the current password to change the password.

> the goal is to use the victim browser logged in session keys for the exploit.

> The delivery CSRF exploit are the same as for reflected XSS. The attacker place the malicious HTML onto a website that they control, and then make victims to visit that website.

## defense

- CSRF tokens: A CSRF token is a unique, secret, and unpredictable value that is generated by the server-side application and shared with the client. On submitting a form, the client must include the correct CSRF token in the request.

- SameSite cookies: A browser security mechanism that determines when a website's cookies are included in requests originating from other websites.

- Referer-based validation: The HTTP Referer header defend by verifying that the request originated from the application's own domain.

## XSS vs CSRF

> CSRF can be described as a "one-way" vulnerability, in that while an attacker can induce the victim to issue an HTTP request, they cannot retrieve the response from that request.

> XSS is "two-way", in that the attacker's injected script can issue arbitrary requests, read the responses, and exfiltrate data to an external domain of the attacker's choosing.
